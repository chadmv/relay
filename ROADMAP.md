Relay is a distributed task/render-farm orchestrator: three Go binaries (relay-server =
HTTP + gRPC + scheduler with an embedded React/Vite SPA; relay-agent worker that holds one gRPC
stream and runs each task as a subprocess; the relay CLI), plus an MCP server and a Perforce
source-provider. Hardening is complete - the 2026-06-10 review's findings are closed and the
seven cross-cutting invariants in CLAUDE.md are enforced and well-tested. They are written in
backend terms but hold across the stack: the generation-ordering rule was rediscovered as a
frontend bug, so `web/` changes are in scope for them too.

The active phase is the embedded web SPA build-out, governed by the `design_handoff_relay_holo`
"Holo" direction (the hi-fi `hifi3-holo-pages.jsx` layer is authoritative; `reference/` is
structure-only). The relayout is done and every surface sits on the shared
`web/src/components/holo` primitives, so what remains is net-new surfaces and backend depth, not
styling. Two rules govern the work: omit data the backend cannot supply rather than fabricating
it, and file the enabler instead; and extract a shared primitive before its third consumer.
Remaining, in rough order: the jobs filter/lane/timeline views, the job-actions wiring, and the
backend enrichers and small endpoints those need. The web-enabler endpoint trio is now fully
shipped, so no backend item currently blocks a frontend one. MCP, agent-runtime and store/schema
items fill in behind. Accessibility and shared-primitive debt is the most reprioritized category
in recent refreshes.

### Later
- [A completed task accepts log appends forever](docs/backlog/bug-2026-08-12-tasklog-terminal-task-append-unbounded.md) - bug, medium; a direct consequence of the hardening family: after the retry guard no production statement can modify a terminal task's row, so an authenticated agent can append log rows to a task it finished indefinitely, with no cap and no retention. Bound it on `finished_at`, not on status.
- [retries is unvalidated end to end, and the retry budget lives only in Go](docs/backlog/bug-2026-08-12-retries-unvalidated-and-budget-only-in-go.md) - bug, medium; **new**. `jobspec.Validate` bounds `Retries` nowhere, and the budget check is the one part of the retry path still outside SQL, with no test covering it.

- [Enrolling with an in-use hostname takes over that worker's identity](docs/backlog/bug-2026-08-12-auto-enroll-hostname-takeover.md) - bug, medium; **new**. `UpsertWorkerByHostname` returns the existing row, then `SetWorkerAgentToken` overwrites its token, locking out the real agent permanently. Config-gated behind `RELAY_ALLOW_AUTO_ENROLL` (off by default), but the enrollment-token path has no revoked check at all.
- [No endpoint can promote or demote an existing user](docs/backlog/feature-2026-08-09-user-role-change-endpoint.md) - feature, medium; `is_admin` is create-only, so a deployment whose sole admin leaves cannot hand over access. Surfaced by the Users tab, which ships with no role-change control because none is possible.
- [Pin SHA-256 of p4d/p4 binaries downloaded by test container](docs/backlog/idea-2026-05-01-p4d-binary-checksum-verification.md) - idea; the last source-side hardening item (test-only supply-chain risk), deprioritized as the phase shifts to the SPA.
- [Wire relay_wait_for_job to SSE job events with a poll fallback](docs/backlog/idea-2026-06-25-mcp-wait-sse-subscribe.md) - idea, low; the adaptive poll already captured most of the win.

## What moved

- **The cross-generation 401 is fixed, and the fix is the frontend instance of the project's own backend rule.** `apiFetch`/`apiStream` now stamp the token a request attached onto the `onUnauthorized` notification, and `AuthProvider`'s listener returns early unless that token still equals `getToken()`. The listener had the CURRENCY half (`statusRef.current === 'anonymous'`) and not the IDENTITY half - exactly the distinction `assignment_epoch` and `worker_id` draw on `tasks.status` writes. Both fences are load-bearing: a failed login sends a null token while `getToken()` is also null, so it passes the identity fence *by equality* and only the currency guard stops it churning state.
- **The item recommended option A and was wrong about when B would be better.** It said a session generation counter would be needed if a token could be *replaced* rather than removed. A compares token values, so `A -> B` and `A -> null -> B` are the same rejection, and A only fails if an identical token string is re-issued - which 32 random bytes rules out. A also adds no state, so it has no bump-ordering hazard, which matters because the item itself flagged that the tidier-looking abort fix is CLAUDE.md Invariant 1's frontend trap.
- **The pipeline was compressed, deliberately.** Phase 1 was collapsed into Phase 2, because the item already carried the mechanism, two candidate fixes with a recommendation, an explicitly rejected option and acceptance criteria. ## API authorization, auth & account lifecycle (api-auth)

1. [The task-log persist-failure limiter is keyed on attacker-controlled input](docs/backlog/bug-2026-08-12-tasklog-err-limiter-attacker-keyed.md) (bug, medium) - `taskLogErrLimiter.shouldLog` keys on `chunk.TaskId` and `chunk.Epoch`, both read off the wire and needing only to parse as a UUID, and on overflow at 1024 entries it resets the whole map rather than suppressing. A NUL byte in `content` is rejected by Postgres at bind time, before the fence evaluates, so the flood path is not fenced: fresh random UUIDs yield one `log.Printf` each, indefinitely, on `log`'s global mutex. Key it on the connection's authenticated worker instead.
2. [Enrolling with an in-use hostname takes over that worker's identity and locks out the real agent](docs/backlog/bug-2026-08-12-auto-enroll-hostname-takeover.md) (bug, medium) - `UpsertWorkerByHostname` is `ON CONFLICT (hostname) DO UPDATE ... RETURNING id`, so it returns the existing worker's row, and `SetWorkerAgentToken` then overwrites that worker's token hash - permanently, surviving a later disable of auto-enroll. `autoEnrollAndRegister` gates only on `status == 'revoked'`; `enrollAndRegister` has no such check at all and `SetWorkerAgentToken` revives revoked to offline. Config-gated (off by default) and adjacent to the deferred CIDR-allowlist item, but the credential invalidation exceeds what "any reachable host may be a worker" grants.
3. [A completed task accepts log appends forever](docs/backlog/bug-2026-08-12-tasklog-terminal-task-append-unbounded.md) (bug, medium) - **new 2026-08-12**, and a direct consequence of the hardening family: a terminal transition deliberately preserves `assignment_epoch` and `worker_id` so trailing chunks still flush, and after the retry guard **no production statement can modify a terminal task's row at all**. So an agent authenticated as that worker can append rows to a task it finished indefinitely, with no cap and no retention - `task_logs` has existed since migration 000001 and nothing in the repo deletes from it. The bound must be time-based on `finished_at`, not a status predicate, which would break the flush a test pins.
4. [handleTaskLog narrows the wire-supplied int64 epoch to int32](docs/backlog/bug-2026-08-12-tasklog-epoch-int32-truncation.md) (bug, low) - `int32(chunk.Epoch)` means `2^32 + E` matches a stored epoch of `E`. Latent rather than live: the assignee predicate now has to match too, and wrapping into a task you already own gains nothing. `handleTaskStatus` compares at int64 width and has no equivalent wrap. One-line guard whenever the path is next touched.
5. [A revoked token keeps receiving SSE events for the life of the held connection](docs/backlog/idea-2026-08-09-sse-revoked-token-keeps-streaming.md) (idea, low) - `/v1/events` authenticates once at connect, so archive and admin-password-reset (which delete a user's tokens expecting that to end their reach) do not terminate a held stream. More consequential now that the stream carries raw subprocess output rather than only status payloads.
6. [No endpoint can promote or demote an existing user](docs/backlog/feature-2026-08-09-user-role-change-endpoint.md) (feature, medium) - `is_admin` is settable only at `POST /v1/users`; `updateUserRequest` is name-only and nothing else mutates the role, so a deployment whose sole admin leaves has no in-product way to hand over administrative access.
