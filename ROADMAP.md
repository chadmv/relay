Relay is a distributed task/render-farm orchestrator: three Go binaries (relay-server =
HTTP + gRPC + scheduler with an embedded React/Vite SPA; relay-agent worker that holds one gRPC
stream and runs each task as a subprocess; the relay CLI), plus an MCP server and a Perforce
source-provider. Hardening is complete - the 2026-06-10 review's findings are closed and the
seven cross-cutting invariants in CLAUDE.md are enforced and well-tested. They are written in
backend terms but hold across the stack: the generation-ordering rule was rediscovered as a
frontend bug, so `web/` changes are in scope for them too.

The active phase is the embedded web SPA build-out, governed by the `design_handoff_relay_holo`
"Holo" direction (the hi-fi `hifi3-holo-pages.jsx` layer is authoritative; `reference/` is
structure-only). The relayout is done and every surface sits on the shared
`web/src/components/holo` primitives, so what remains is net-new surfaces and backend depth, not
styling. Two rules govern the work: omit data the backend cannot supply rather than fabricating
it, and file the enabler instead; and extract a shared primitive before its third consumer.
Remaining, in rough order: finish the admin console (only Invites is left, its list half blocked
on `GET /v1/invites`), the Profile and Schedule-detail pages, the jobs filter/lane/timeline views,
and the backend enrichers and small endpoints those need. MCP, agent-runtime and store/schema items
fill in behind. Accessibility and shared-primitive debt is the most reprioritized category this
refresh.

## What moved

- **The epoch-0 log-forgery bug is fixed and closed** (2026-08-12, tasklog-append-assignee-fence): `AppendTaskLog`'s fence CTE gained a third predicate, `AND t.worker_id = sqlc.arg(worker_id)`, and `handleTaskLog` now takes the connection's authenticated worker id, resolved at registration and never read off the wire. One statement, one round trip, no proto change.
- **The item's own framing was wrong, and the correction is the interesting part.** It described the hole as "never-claimed tasks via Epoch 0". The fence compares an integer, so the reachable set was *every task in the database* - including one running live on another worker, where forged lines interleave with genuine output in an operator's live tail. That case is the highest-impact one and the item's title hid it.
- **`=` is load-bearing, and the test that proves it had to be found the hard way.** `tasks.worker_id` is nullable, so a rewrite to `IS NOT DISTINCT FROM` would re-open the exact hole. The planner caught that the spec's proposed zero-value-worker case does **not** catch that rewrite (on a claimed task both forms are false) and added a never-claimed + zero-value case where NULL sits on both sides. A mutation check confirmed exactly that one case goes red.
- **Four items filed, one closed; open count 56 -> 59.** All four came out of Phase 4 review, none was in the original scope: [taskstatus-update-unauthenticated-epoch-zero](docs/backlog/bug-2026-08-12-taskstatus-update-unauthenticated-epoch-zero.md) (high), [auto-enroll-hostname-takeover](docs/backlog/bug-2026-08-12-auto-enroll-hostname-takeover.md), [tasklog-err-limiter-attacker-keyed](docs/backlog/bug-2026-08-12-tasklog-err-limiter-attacker-keyed.md), and [tasklog-epoch-int32-truncation](docs/backlog/bug-2026-08-12-tasklog-epoch-int32-truncation.md).

## API authorization, auth & account lifecycle (api-auth)

1. [Any enrolled agent can set any task's status via the unauthenticated epoch fence, permanently wedging it](docs/backlog/bug-2026-08-12-taskstatus-update-unauthenticated-epoch-zero.md) (bug, high) - the sibling of the just-closed log-forgery bug, on the status path. `handleTaskStatus` compares `task.AssignmentEpoch != upd.Epoch` with no sender check and `UpdateTaskStatus` fences on the epoch alone, so `Epoch: 0` reaches any never-claimed task. `DONE` unblocks dependents against work that never ran; `FAILED` cascades the transitive DAG in one message; `RUNNING` writes a NULL `worker_id` that no requeue path can recover (all are keyed `WHERE worker_id = $1`), leaving cancel as the only remedy. Not a copy-paste of the log-path fix: `Dispatcher.failClaimedTask` is a second caller, and a sentinel meaning "skip the check" would fail open.
   related to [tasklog-append-assignee-fence](docs/backlog/closed/bug-2026-08-09-tasklog-append-unauthenticated-epoch-zero.md) (merged); read its spec first
2. [The task-log persist-failure limiter is keyed on attacker-controlled input](docs/backlog/bug-2026-08-12-tasklog-err-limiter-attacker-keyed.md) (bug, medium) - `taskLogErrLimiter.shouldLog` keys on `chunk.TaskId` and `chunk.Epoch`, both read off the wire and needing only to parse as a UUID, and on overflow at 1024 entries it resets the whole map rather than suppressing. A NUL byte in `content` is rejected by Postgres at bind time, before the fence evaluates, so the flood path is not fenced: fresh random UUIDs yield one `log.Printf` each, indefinitely, on `log`'s global mutex. Key it on the connection's authenticated worker instead.
3. [Enrolling with an in-use hostname takes over that worker's identity and locks out the real agent](docs/backlog/bug-2026-08-12-auto-enroll-hostname-takeover.md) (bug, medium) - `UpsertWorkerByHostname` is `ON CONFLICT (hostname) DO UPDATE ... RETURNING id`, so it returns the existing worker's row, and `SetWorkerAgentToken` then overwrites that worker's token hash - permanently, surviving a later disable of auto-enroll. `autoEnrollAndRegister` gates only on `status == 'revoked'`; `enrollAndRegister` has no such check at all and `SetWorkerAgentToken` revives revoked to offline. Config-gated (off by default) and adjacent to the deferred CIDR-allowlist item, but the credential invalidation exceeds what "any reachable host may be a worker" grants.
4. [handleTaskLog narrows the wire-supplied int64 epoch to int32](docs/backlog/bug-2026-08-12-tasklog-epoch-int32-truncation.md) (bug, low) - `int32(chunk.Epoch)` means `2^32 + E` matches a stored epoch of `E`. Latent rather than live: the assignee predicate now has to match too, and wrapping into a task you already own gains nothing. `handleTaskStatus` compares at int64 width and has no equivalent wrap. One-line guard whenever the path is next touched.
5. [A revoked token keeps receiving SSE events for the life of the held connection](docs/backlog/idea-2026-08-09-sse-revoked-token-keeps-streaming.md) (idea, low) - `/v1/events` authenticates once at connect, so archive and admin-password-reset (which delete a user's tokens expecting that to end their reach) do not terminate a held stream. More consequential now that the stream carries raw subprocess output rather than only status payloads.
6. [No endpoint can promote or demote an existing user](docs/backlog/feature-2026-08-09-user-role-change-endpoint.md) (feature, medium) - `is_admin` is settable only at `POST /v1/users`; `updateUserRequest` is name-only and nothing else mutates the role, so a deployment whose sole admin leaves has no in-product way to hand over administrative access. Needs a last-active-admin guard mirroring archive's.
7. [POST /v1/reservations returns 500 for a nonexistent user_id](docs/backlog/bug-2026-08-09-create-reservation-500-on-client-error.md) (bug, medium) - every `CreateReservation` error funnels to a single 500, so a client mistake surfaces as a server error via the users FK; the handler also skips worker-existence and inverted-window checks. `internal/api/agent_enrollments.go` has the same funnel shape, so check whether this is one handler or a shared habit.
8. [Audit log for archive/unarchive actions](docs/backlog/idea-2026-05-06-audit-log-archive-unarchive.md) (idea) - archive/unarchive are recorded nowhere; the narrow first slice of an audit trail, which the broad sibling below would subsume once an audit table lands.
9. [Audit log for privileged admin-console actions](docs/backlog/feature-2026-06-26-audit-log-admin-console-actions.md) (feature, low) - the broad audit trail (invite creation, admin password reset, worker disable/enable/revoke, plus archive/unarchive); introduces the audit table the narrow item also needs. Now that the admin console has real privileged actions shipping, this has concrete subjects to record.
