Relay is a distributed task/render-farm orchestrator: three Go binaries (relay-server =
HTTP + gRPC + scheduler with an embedded React/Vite SPA; relay-agent worker that holds one
gRPC stream and runs each task as a subprocess; the relay CLI), plus an MCP server and a
Perforce source-provider. The hardening phase is complete - the 2026-06-10 review's
concurrency/correctness findings are all closed, and the cross-cutting invariants (epoch
fencing on every task-status write, one bounded sender per gRPC stream, identity-checked
teardown, the single job-spec pipeline, no interior pointers across locks, the single JSON
entry point) are enforced and well-tested. The active phase is the embedded web SPA
build-out, governed by the `design_handoff_relay_holo` "Holo" design direction - a glassy dark
UI. The whole-app hi-fi Holo relayout is complete - every shipped surface uses the shared
`web/src/components/holo` primitive set - so the remaining work is net-new surfaces and backend
depth, not styling. The active program is the **admin console**, whose route shell (admin-gated
`/admin/:tab`, registry-driven tab bar), the **Users**, **Agent enrollments** and
**Reservations** tabs all shipped 2026-08-09; only the server-overview tab (a quick win over
existing stats) and Invites (list half still blocked) remain, each one registry entry away, and the
enrollments tab left behind a shared token-reveal dialog that Invites will reuse. The **SSE task-log
publishing enabler and its first consumer both landed 2026-08-09**: `GET /v1/events?task_id=` is a
real live-log source, and the SPA now tails a task log live in both the job-detail Log tab and a
full-screen route, which also made it the app's first SSE client (`fetch` + `ReadableStream`, since
`EventSource` cannot carry a bearer header). The MCP live-log idea keeps the same enabler available.
Behind that: Profile pages, the Schedule detail page, the jobs filter/lane/timeline views, and the
backend enrichers that would fill out the job-detail page (job/task timing). The small backend
endpoints several of them still need (invites/sessions list, job retry, enrollment revoke, job/task
timing) are filed under the Backend API & server enablers theme; the remaining MCP, agent, and
store/schema items fill in behind the SPA work.

## API authorization, auth & account lifecycle (api-auth)

1. [Any enrolled agent can append log lines to any never-claimed task via Epoch 0](docs/backlog/bug-2026-08-09-tasklog-append-unauthenticated-epoch-zero.md) (bug, medium) - `handleTaskLog` fences on `assignment_epoch` but never checks sender identity, and the column defaults to `0`, so any enrolled agent can forge log content onto any unclaimed task. Pre-existing; amplified because forged lines now fan out live. The fix stays one statement (fence on assignee as well as epoch), so it does not cost the ingest path a round trip.
2. [A revoked token keeps receiving SSE events for the life of the held connection](docs/backlog/idea-2026-08-09-sse-revoked-token-keeps-streaming.md) (idea, low) - `/v1/events` authenticates once at connect, so archive and admin-password-reset (which delete a user's tokens expecting that to end their reach) do not terminate a held stream. More consequential now that the stream carries raw subprocess output rather than only status payloads.
3. [No endpoint can promote or demote an existing user](docs/backlog/feature-2026-08-09-user-role-change-endpoint.md) (feature, medium) - `is_admin` is settable only at `POST /v1/users`; `updateUserRequest` is name-only and nothing else mutates the role, so a deployment whose sole admin leaves has no in-product way to hand over administrative access. Needs a last-active-admin guard mirroring archive's.
4. [POST /v1/reservations returns 500 for a nonexistent user_id](docs/backlog/bug-2026-08-09-create-reservation-500-on-client-error.md) (bug, medium) - every `CreateReservation` error funnels to a single 500, so a client mistake surfaces as a server error via the users FK; the handler also skips worker-existence and inverted-window checks. `internal/api/agent_enrollments.go` has the same funnel shape, so check whether this is one handler or a shared habit.
5. [Audit log for archive/unarchive actions](docs/backlog/idea-2026-05-06-audit-log-archive-unarchive.md) (idea) - archive/unarchive are recorded nowhere; the narrow first slice of an audit trail, which the broad sibling below would subsume once an audit table lands.
6. [Audit log for privileged admin-console actions](docs/backlog/feature-2026-06-26-audit-log-admin-console-actions.md) (feature, low) - the broad audit trail (invite creation, admin password reset, worker disable/enable/revoke, plus archive/unarchive); introduces the audit table the narrow item also needs. Now that the admin console has real privileged actions shipping, this has concrete subjects to record.

## Store schema integrity & query performance (store-schema)

1. [IncrementTaskRetryCount can resurrect a cancelled task](docs/backlog/bug-2026-06-26-retry-resurrects-cancelled-task.md) (bug, high) - the only `tasks.status` writer with no epoch/status guard; a cancel racing a retry re-queues a cancelled task and `RecomputeJobStatus` pulls the job out of `cancelled`. The lone unguarded epoch-fence path - fix before/with the retry endpoint in [web-enabler-backend-endpoints](docs/backlog/feature-2026-06-26-web-enabler-backend-endpoints.md).

[handleCancelJob reads the job row without FOR UPDATE](docs/backlog/bug-2026-07-01-cancel-job-for-update-lock.md) (bug, low) - the job-row read in the cancel path is unlocked, so concurrent cancels (and cancel-vs-terminal-recompute) are not fully serializable on the job side; a `FOR UPDATE` closes the residual TOCTOU. Belt-and-suspenders companion to the retry bug above.
3. [Jobs stats 24h buckets rely on updated_at finish proxy](docs/backlog/bug-2026-06-05-jobs-stats-24h-updated-at-proxy.md) (bug, low) - correct today; a conditional watch that becomes inaccurate only if a job-retry endpoint that re-opens terminal jobs is added - now proposed in [job-retry-action](docs/backlog/feature-2026-07-01-job-retry-action.md), so schedule the two together.
4. [Persist and expose step_index/step_total on task_logs](docs/backlog/feature-2026-06-26-persist-expose-step-index-total.md) (feature, low) - add nullable step columns and thread them through AppendTaskLog (under the epoch fence) and the logs API; the prerequisite that unblocks retiring the synthetic step-marker line.
   blocks [remove-synthetic-step-marker](docs/backlog/idea-2026-04-26-remove-synthetic-step-marker.md)
5. [Task list ordering is unspecified and shifts](docs/backlog/bug-2026-08-09-task-list-ordering-has-no-tiebreaker.md) (bug, medium) - a job's tasks all share one transaction-constant `created_at` and `ORDER BY created_at` has no tiebreaker, so the order is undefined and visibly shifts as rows are updated. Blocked index-based task routing outright. The cheap tiebreaker and a meaningful declaration-order column are separable.
6. [Remove dead 'queued'/'dispatched' status vocabulary](docs/backlog/idea-2026-07-01-dead-status-vocabulary.md) (idea, low) - `CancelJobTasks` and `CountActiveJobsForSchedule` filter on statuses the migration 000019 CHECK constraints make unreachable for those tables; cosmetic, contradicts the schema.
