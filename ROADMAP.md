Relay is a distributed task/render-farm orchestrator: three Go binaries (relay-server =
HTTP + gRPC + scheduler with an embedded React/Vite SPA; relay-agent worker that holds one gRPC
stream and runs each task as a subprocess; the relay CLI), plus an MCP server and a Perforce
source-provider. Hardening is complete - the 2026-06-10 review's findings are closed and the
seven cross-cutting invariants in CLAUDE.md are enforced and well-tested. They are written in
backend terms but hold across the stack: the generation-ordering rule was rediscovered as a
frontend bug, so `web/` changes are in scope for them too.

The active phase is the embedded web SPA build-out, governed by the `design_handoff_relay_holo`
"Holo" direction (the hi-fi `hifi3-holo-pages.jsx` layer is authoritative; `reference/` is
structure-only). The relayout is done and every surface sits on the shared
`web/src/components/holo` primitives, so what remains is net-new surfaces and backend depth, not
styling. Two rules govern the work: omit data the backend cannot supply rather than fabricating
it, and file the enabler instead; and extract a shared primitive before its third consumer.
The web-frontend theme's top twenty-two items shipped in the 2026-09-02 batch (the Jobs search,
My jobs toggle and Timeline; the Schedules strip, search and LAST JOB link; the reservations panel;
the resizable job-detail split; the structured job builder; the dialog guard and layering scale;
table accessibility; the vite/vitest upgrade), with their server filters and stats endpoints.
What remains in web is accessibility and shared-primitive debt plus the follow-ups those reviews
filed. The backend enablers in front of it are now bounds on agent-supplied input: how many
distinct workspace keys a job author can mint, the size of the key itself, and the two unpaged
reads that still run before the HTTP listener. MCP and store/schema items fill in behind.

## Now / Next / Later

### Now

- [A job author controls how many p4 client specs and workspace directories every agent creates](docs/backlog/idea-2026-09-04-a-job-author-controls-how-many-p4-clients-each-agent-creates.md) - idea, medium; **new this refresh and it leads Now**, because it is a live consequence of what just shipped. `shortID` now derives from `SourceKey`, so the p4 client name and the workspace directory are both functions of the exclusion set, and `CreateStreamClient` runs on every Prepare about 200 lines BEFORE a bogus exclusion can be refused. Sixteen arbitrary strings that name nothing still mint a key, a short id, a directory and a persistent client spec on the shared Perforce server. Before the change the count was bounded by the number of real streams, which an author cannot invent. The obvious fix does not work: the probe uses a client-form filespec, so it cannot run before the client exists.
- [`worker_workspaces.source_key` is agent-supplied, unbounded, and inside a primary key](docs/backlog/idea-2026-09-04-worker-workspaces-source-key-is-unbounded-in-a-primary-key.md) - idea, medium; **promoted from Next, and the item above is why.** The exclusion slice kept its own key short - exactly 20 bytes over the stream, now pinned by a test - so it routed around this rather than closing it. What changed is the number of distinct keys one submitter can mint per stream, which was one and is now unbounded, and every one of them reaches this primary key through `applyInventory`'s single transaction.
- [`ReconcileOnStartup` lists every overdue schedule with no LIMIT, also before the listener](docs/backlog/bug-2026-09-04-reconcileonstartup-lists-every-overdue-schedule-unbounded.md) - bug, medium; **new this refresh.** The boot-sweep item's paging bounded one pre-listener read; this is a second one on the same path that was never in that item's scope - `SELECT *` with no LIMIT over every enabled overdue row. So "the boot's peak memory is one page" is true of the sweep and false of the boot. The per-owner cap does not close it either: this result set is every overdue row across all owners, not one owner's holdings.
- [A wall-clock deadline on the boot sweep](docs/backlog/feature-2026-09-04-wall-clock-deadline-on-the-boot-sweep.md) - feature, medium; **new this refresh**, carrying the duration question the cap slice settled OUT rather than deferring silently. A count cap bounds the sweep's starting work set only, and the paged sweep takes a fresh snapshot per page. Read the item's opening constraint before scoping it: a truncated sweep UNDER-REPORTS, so the boot line must not present a partial count as a total - decide what it says when the deadline fires before deciding the number.
- [`pgdsn`'s DSN user-arm guard is RED for any run as root](docs/backlog/bug-2026-09-04-pgdsn-user-guard-is-red-for-any-run-as-root.md) - bug, medium; **new this refresh, and a `quick win`.** The test injects `?user=root` and asserts the derived default user is not `"root"`, but `wantDefaultUser` falls through to `pgx.ParseConfig`, which derives the OS user. So the CLAUDE.md-recommended local container - the reliable `-race` route on this machine, and the only local way to run the `//go:build !windows` files at all - is red on a clean tree. Green in CI only because that runner is not root. Two lanes hit it independently in one batch, which is what makes it worth clearing early.
- [`source.sync` has no entry-count bound, and each `#head` entry is one ResolveHead round trip](docs/backlog/idea-2026-09-04-source-sync-has-no-entry-count-bound.md) - idea, medium; **promoted from Next.** The exclusion slice bounded exclusions at 16 and left includes unbounded, so this is now an asymmetry inside one spec field rather than a general gap: capped on one axis, open on the other, with `Prepare` running one `ResolveHead` per `#head` entry.

[A schedule fires under its owner's identity with no credential check at fire time](docs/backlog/bug-2026-08-29-a-schedule-outlives-its-owners-credentials.md) (bug, medium) - **new 2026-08-29.** `ListEligibleScheduledJobs` filters on `enabled` and `next_run_at` only, and `fireOne` creates the job under `row.OwnerID` with nothing authenticated at fire time. Filed despite being ~300x slower than `POST /v1/jobs`, because rate is not the axis: **the load survives the remedy an operator reaches for first.** Revoking a token does not stop it and there is no user-disable flag, so the only working rungs are deleting each schedule or deleting the user.
2. [Deleting a worker frees its hostname to whoever claims it first, at an attacker-observable instant](docs/backlog/bug-2026-08-26-deleting-a-worker-frees-its-hostname-to-a-race.md) (bug, medium) - **new 2026-08-26.** The 2026-08-25 guards closed takeover by refusing any hostname with a row; delete removes the row, which is the feature. The gap is that the operator does not control who claims it next: `autoEnrollAndRegister` takes no row lock, so its insert blocks on the deleting xact at the unique index rather than failing fast, and there is no rate limit on gRPC registration. README now presents delete as the remedy for a machine re-provisioned in place, so the intended use is precisely to free a hostname for a specific machine to re-take. Fix is documentation - name the race and the two sequences that avoid it.

[Re-enrolling a deleted worker mints a new id, so every reservation that fenced it silently stops](docs/backlog/bug-2026-08-26-re-enrolling-a-deleted-worker-escapes-its-reservations.md) (bug, medium) - **new 2026-08-26.** `reservedIDs` is consulted only as an exclusion set over live rows, so a reservation naming W keeps W out of general dispatch. Delete scrubs the id correctly; the gap is one step later, when the machine returns under a new uuid and is no longer fenced. README covers only the sub-case where the array empties - the multi-worker case is worse because it looks healthy.

[The delete response's counts are unpinned across the API/CLI boundary](docs/backlog/bug-2026-08-26-attribution-cleared-is-unpinned-across-the-api-cli-boundary.md) (bug, medium) - **new 2026-08-26.** Two hand-written structs with independently spelled json tags and a hand-written CLI fixture, so a rename or an added fifth count leaves both packages green while the shipped command prints `0`. `attribution_cleared` is the sharp case: it counts the run-attribution history the delete destroys, and the handler's own comment calls the body the ONLY record of that. [The counters payload cannot say "not measured"](docs/backlog/idea-2026-08-21-counters-payload-cannot-say-not-measured.md) (idea, low) - **new 2026-08-21**, and it is `GET /v1/server/counters`'s own subject one layer down. With both gRPC caps disabled, `Accept` returns connections unwrapped and does no accounting, so every `levels` field reads 0 however many are live - and because the section is PRESENT, the payload affirmatively asserts "this control ran and stopped nothing" where the truth is "this control measured nothing". A false statement rather than an ambiguous one. Two wrong closures are named and forbidden up front: making the section absent (which would weaken `absent` for all four sections) and accounting on the disabled path (which `TestLimitListener_ZeroDisables` reddens). **Cheapest during slice 2**, because it is a contract expansion across every section and expensive once four exist.

[rejected_total is forgeable and its remedy helps the forger](docs/backlog/idea-2026-08-21-rejected-total-is-forgeable-and-its-remedy-helps-the-forger.md) (idea, medium) - **new 2026-08-21.** Only `worker_id` is authenticated on an incoming chunk, and nothing rate-limits task-log CHUNKS - the ingest budget bounds LINES - so any enrolled agent can drive `task_log_fence.counts.rejected_total` up smoothly and indefinitely by naming task ids it does not own. That produces exactly the "climbs steadily on a healthy fleet" signature README attributes to a too-small `RELAY_TASKLOG_TRAILING_WINDOW`, **whose documented remedy is to RAISE the window - widening the hole the window exists to bound.** No disclosure problem (an agent cannot read the endpoint and the payload carries no identifiers); the exposure is griefing and misdirection of the one signal. Merged with the priced LEFT JOIN reason-split rather than filed separately, because the split is what would resolve it.
7. [A revoked agent credential survives on a held connection](docs/backlog/idea-2026-08-21-revoked-agent-credential-survives-on-a-held-connection.md) (idea, medium) - **new 2026-08-21**, in Next. Sibling of item 9 below rather than an absorption, because the two transports have different registries, revocation paths and costs - but a pair describing one defect must not disagree about the tolerance, so agreeing on ONE is an acceptance criterion. Proposed fix is a `Registry.CloseIfPresent(workerID)` after the DB write; `Registry` already has `UnregisterIf` and `workerSender.Close`. **Scope correction from the slice**: new dispatches stop at once (revocation sets `workers.status` to `revoked` and the dispatcher selects only `online`/`stale`); what survives is in-flight execution and its `task_logs`/`tasks.status` writes, which fence on epoch and `worker_id` and never on worker status.

[Per-stream log budget renewal is unpriced](docs/backlog/idea-2026-08-21-per-stream-log-budget-renewal-is-unpriced.md) (idea, low) - **new 2026-08-21**, and the honest residual of `MaxConcurrentStreams(1)`. ## Store schema integrity & query performance (store-schema)

1. [`CreateJobFromSpec` issues one round trip per `depends_on` entry](docs/backlog/bug-2026-08-29-createjobfromspec-inserts-one-dependency-edge-per-round-trip.md) (bug, medium) - **new 2026-08-29, and it takes this slot from the count-bounds item that closed out of it**, which had cleared `depends_on` as "no algorithmic blowup". That was right about the validator and silent about the writer: `detectCycle` is linear, and `CreateJobFromSpec` then issues one `CreateTaskDependency` round trip per ENTRY, sequentially, inside the caller's transaction. **The worst case is a TWO-task spec** - `Validate` checks each name for membership only and never dedupes, `detectCycle` handles repeats correctly and so ACCEPTS them, and the INSERT is `ON CONFLICT DO NOTHING`, so one name repeated to the body limit is ~209,700 round trips producing exactly one row. `maxTasksPerJob` does not reach it, and batching must dedupe first or a `CopyFrom` just relocates the cost.
2. [There is no backoff between a failed task and its redispatch](docs/backlog/bug-2026-08-27-no-backoff-between-a-failed-task-and-its-redispatch.md) (bug, medium) - **new 2026-08-27**, scoped out of the retry-bounds slice and the reason its cap came out low. `IncrementTaskRetryCount` returns the task to `pending`, `handleTaskStatus` immediately calls `NotifyTaskSubmitted`, the dispatcher wakes: nothing waits. So a millisecond-failing command burns its whole budget in under a second, and the retry feature's own use cases - a flaky mount, a contended license server - are exactly the faults a wait would clear and an immediate retry will not. The natural shape is a `not_before` column plus a `GetEligibleTasks` predicate, with one non-obvious consequence: a time-gated task needs something to wake an idle dispatcher when its wait expires.
3. [A database CHECK on `tasks.retries` / `tasks.timeout_seconds`](docs/backlog/idea-2026-08-27-db-check-constraint-on-retries-and-timeout-seconds.md) (idea, low) - **new 2026-08-27**, the column-level guarantee the retry-bounds slice declined. Migrations run on startup, so a plain `ADD CONSTRAINT` refuses to boot the binary on exactly the population that has the bug, and `NOT VALID` converts that loud failure into a silently stuck task. The pre-existing-row decision (clamp, fail to boot, or two-release `VALIDATE`) IS the item; the SQL is four lines. A caller-side AST guard stands in for it today, which protects the call graph rather than the column.
