# A server-side bound on the cost of ?q= text search

## Summary
The ?q= filter on GET /v1/jobs and GET /v1/scheduled-jobs is an unbounded substring scan: on a 200k-row jobs table a no-match needle measured about 283 ms of database CPU against 10.8 ms for the unfiltered list, roughly a 26x amplifier, and nothing on the server bounds it. README states the cost honestly and points at the client-side debounce, which is not a bound because any authenticated caller can issue the request directly.

## Context
Found by the security lens of lane JB (PR #178) and deliberately left out of that lane's scope. Lane JF's spec proposed a rate limit on ?q= separately; this item merges both.

## Proposal
- An env-configurable statement_timeout on the pool (or a per-statement timeout for the text-count and text-list statements) so one needle cannot hold a connection for seconds.
- The existing per-IP RateLimit applied to authenticated reads carrying q, with its own bucket so list polling without q is unaffected.
- Measure the amplifier again after either lands and record the input (row count, needle) with the number.

## Resolution
Two controls shipped, and neither makes the scan cheaper.

`RELAY_JOB_SEARCH_RATE_LIMIT` (default `120:10s`) is a per-user bucket over `GET /v1/jobs` and
`GET /v1/scheduled-jobs`, shared between them and separate from the write-side submit bucket. It
reuses `userRateLimitKey` and `rateLimiter` from that slice rather than re-implementing either.
`RELAY_DB_STATEMENT_TIMEOUT` (default `30s`) applies `statement_timeout` to every pooled
connection.

**This item's proposal was not implementable as written**, and correcting it is most of the
design. "The existing per-IP `RateLimit` applied to authenticated reads" would have inherited the
proxy collapse the user key exists to avoid; this needed a second INSTANCE of the user-keyed
mechanism, not a second mounting. And "a per-statement timeout for the text-count and text-list
statements" names a set that does not exist: only the COUNT arms are split text/non-text, every
LIST arm is one statement serving both cases, and 33 generated structs carry a top-level `Q`. So
a per-statement timeout would either cover unfiltered polling, which this item forbids, or need
branching at all 33 sites.

**The priority order was backwards.** At the measured cost no plausible statement timeout binds,
so the rate bucket is the load-bearing control and the timeout is a floor under a query with no
owner. The failure mode is pool occupancy against 25 connections shared with the dispatcher, log
ingest and the watchdog, not CPU burn.

**The placement is the heart of it.** The bucket is charged INSIDE the handler at the point
`parseFilterQ` returned a non-nil needle, not as middleware, because `parseFilterQ` discards
percent-decoding errors and takes only the first of a repeated parameter - a middleware predicate
would be a second implementation of the needle-present decision, able to disagree with the
validated one. `?q=%20%20`, which the parser trims to absent, is the discriminating input and is
not charged.

**`maxFilterQRunes` bounds the wrong axis, and the measurement shows why.** It caps per-row work
while the dominant term is rows scanned, and the worst input is short: a needle matching nothing
costs an order of magnitude more than one matching 2,000 rows, because a match fills the page
early and the walk stops. The count and the list also do not scale together - the count has no
`LIMIT` and joins `users`, so it walks regardless.

**The default's real constraint is relay's own client, not an adversary.** The jobs view
refetches five lanes every three seconds, each carrying the needle while one sits in the search
box. At the measured cost a full window still exceeds one box, so this is a fairness bound
between principals and not a CPU budget, and it degrades linearly in the number of accounts an
actor controls. All three points are stated in README rather than left implied.

The measurement is recorded with its inputs in `docs/retros/2026-09-04-q-cost-measurement.md` and
regenerated by `scripts/qcost`; README carries only the properties that do not decay.
