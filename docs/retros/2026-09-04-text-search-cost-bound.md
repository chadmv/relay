# Session Retro: 2026-09-04 - Text-Search Cost Bound

**TL;DR:** Typing in the jobs search box makes the database scan every row, and a search that
matches nothing is the most expensive kind. Any logged-in user could fire those as fast as they
liked. This session added two limits: how often one person can search, and how long any single
query may run. Neither makes the search faster - that is a different item. The interesting part
was that the backlog item's own prescription could not be built as written, in two separate ways,
and finding that out was most of the work.

## Handoff

Lane F of a six-item batch over ROADMAP.md's Now section, and the last of the six. Closed
[[feature-2026-09-03-server-side-bound-for-text-search]]. Twelve commits: spec, plan, eight
implementation commits, the measurement plus README, and a README correction from review.

`RELAY_JOB_SEARCH_RATE_LIMIT` (default `120:10s`) is a per-user bucket over `GET /v1/jobs` and
`GET /v1/scheduled-jobs`, shared between them, separate from the submit bucket, and reusing
`userRateLimitKey` and `rateLimiter` rather than re-implementing either.
`RELAY_DB_STATEMENT_TIMEOUT` (default `30s`) applies `statement_timeout` to every pooled
connection via `RuntimeParams`, before the pool is built.

**The bucket is charged INSIDE the handler**, at the point `parseFilterQ` returned a non-nil
needle. `?q=%20%20` is the discriminating input: the parser trims it to absent, so it is not
charged, while a middleware predicate would have seen a present parameter.

Verify: 23 packages green, both vet lanes clean. Measurement in
`docs/retros/2026-09-04-q-cost-measurement.md`, regenerated by `scripts/qcost`.

## What Was Built

- `parseDBStatementTimeout` and `applyStatementTimeout` in `cmd/relay-server`, with a boot refusal
  for any value Postgres would read as disabled.
- `Server.searchRateLimiter()`, gated by `sync.Once` on the Server, so the bucket is built once
  per Server rather than once per `Handler()` call.
- `listQueryError` logging the SQLSTATE behind a list 500, so a statement timeout is diagnosable
  rather than an anonymous 500.
- `scripts/qcost`, which seeds its own throwaway Postgres and regenerates the measurement.

## Key Decisions

- **Pool-wide, not per-statement.** The item asked for a timeout on "the text-count and text-list
  statements". Only the COUNT arms are split text/non-text; every LIST arm is one statement
  serving both cases, and 33 generated structs carry a top-level `Q`. A per-statement timeout
  would either cover unfiltered polling, which the item forbids, or need branching at 33 sites.
- **Applied in Go, never through the DSN.** `migrateDSN` is derived from the DSN by prefix
  rewriting, so a DSN-carried value would reach migrations - and a long `CREATE INDEX` is exactly
  what must not be cut short. As configured, migrations are structurally out of reach because
  `store.Migrate` opens its own connection before the pool exists.
- **The two handlers deliberately differ in precedence.** `handleListScheduledJobs` answers 401
  before `parsePage`; the new jobs charge sits after `parsePage`, the sort-versus-filter guard,
  `rejectRepeatedParams` and all of `parseJobFilters`. They agree on the outcome for a well-formed
  request and must disagree on precedence, because the new refusal may not outrank an existing 400.

## What Went Wrong and What Changes

**The item's prescription was unbuildable in two independent ways, and both were found by reading
the tree rather than by trying it.** "Apply the existing per-IP `RateLimit` to authenticated
reads" would have inherited the proxy collapse the user key exists to avoid. And the per-statement
timeout named a set of statements that does not exist. Neither is a preference disagreement; both
are factual errors in the item, and an implementer who took it literally would have built the
wrong control twice.

**The item's priority order was backwards.** It leads with the statement timeout. At the measured
cost no plausible timeout binds, so the rate bucket is the load-bearing control and the timeout is
a floor under a query with no owner. The failure mode is pool occupancy against 25 connections
shared with the dispatcher, log ingest and the watchdog, not CPU burn.

**A boundary value in the spec was an example, not the boundary.** The spec said a `100us` timeout
would round to Postgres's DISABLED sentinel and must be refused. True, but `100us` is one member
of that set: the boundary is `999999ns`, because `time.Duration` is nanoseconds and
`Milliseconds()` truncates toward zero. A table testing only `100us` passes against a parser that
refuses everything below one second. The plan caught it and put `999999ns` first.

**The measurement changed what the item believed about its own subject.** The worst case is the
needle that matches NOTHING, an order of magnitude more expensive than one matching 2,000 rows,
because a match fills the page early and the walk stops. That is the concrete reason
`maxFilterQRunes` bounds the wrong axis: it caps per-row work while the dominant term is rows
scanned, and the worst input is short. The count and the list also do not scale together. None of
this was in the item.

**The default's real constraint is relay's own client.** The jobs view refetches five lanes every
three seconds, each carrying the needle while one sits in the search box. The item inherited
README's debounce framing as if the SPA were quiet; it is not.

**The conductor shipped a documentation defect and review caught it.** The finished README carried
the measured millisecond ranges verbatim. This project's own rule puts measurement provenance in a
record of a moment - a commit message, spec, or retro - which cannot drift; a number in README is
read as current long after the hardware or the table shape has moved, and nothing pins it. The
numbers moved to the retro and README kept only the properties that do not decay. Note the shape:
the last task of a killed agent was finished by hand and had no engineer-side review, and that is
exactly the commit the defect was in.

**An expected survival was recorded rather than engineered away.** Mutating `main.go`'s
`httpServerDeps` literal to zero reddens nothing, because every existing wiring guard scopes
itself to fields feeding `s.Counters`. A sibling lane measured the same gap for its own field. The
plan named it in advance instead of it being discovered in review, which is the improvement.
